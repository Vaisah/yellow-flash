# Yellow Flash: the window

The desktop app's UI: React 18 and TypeScript, built with Vite and shown by Wails v2 in the
system's web view (WebView2 on Windows, WebKitGTK on Linux). All the work happens in the Go
backend; this code shows it and calls it.

## Running it

From the repository root, with the real backend:

```sh
wails dev     # the app with hot reload; http://localhost:34115 also serves it to a browser,
              # still talking to the real Go backend
```

From this folder, the UI alone with a simulated backend:

```sh
npm ci
npm run dev   # http://localhost:5173
```

In `npm run dev` there is no Wails runtime, so `src/main.tsx` installs `src/dev/mockBackend.ts`,
which fakes the bindings and a few running downloads. It is loaded only in development builds and
is never bundled into the app.

| Command | What it does |
|---|---|
| `npm run dev` | Vite dev server, mock backend |
| `npx tsc -b` | type-check only |
| `npm run build` | type-check, then build into `dist/` |

`wails build` runs `npm ci` and `npm run build` itself, then embeds `dist/` in the Go binary
(`//go:embed all:frontend/dist` in `main.go`). `dist/` is committed so the Go module builds
without Node.

## Layout

```
src/
  main.tsx              entry: installs the mock backend in dev, renders App
  App.tsx               the window: state, toolbar actions, which dialog is open, event listeners
  api.ts                backend(), event helpers (onEvent, onProgress…), clipboard, opening links
  wails.d.ts            the types of every Go binding the UI calls (window.go.main.App)
  types.ts              the data the bindings exchange (Download, Queue, Options…)
  hooks/useDownloads.ts the download list: loaded once, then kept current by events
  components/
    Chrome.tsx          title bar, menus, toolbar, sidebar (categories, disk meter), status bar
    DownloadTable.tsx   the list, sorting, the right-click menu
    DetailsPanel.tsx    the selected download: progress, segment map, server location
    Dialogs.tsx         Add URL, Options, Delete, Download Complete
    SchedulerDialog.tsx queues, schedules, data cap
    MediaGrabberDialog.tsx  videos through yt-dlp
    BatchDialog.tsx, ChecksumDialog.tsx, SpeedLimiterDialog.tsx
    Modal.tsx           the dialog frame every dialog uses
  lib/                  formatting, file categories, plain-language error explanations
  dev/mockBackend.ts    the simulated backend (dev only)
  style.css             all the styling
wailsjs/                generated by Wails; not imported (see below)
```

## Talking to the backend

Every exported method of the Go `App` struct is a binding. The UI calls it through `backend()`:

```ts
import { backend, errorMessage } from './api'

const info = await backend().DiskSpace(settings.downloadDirectory)
try {
  await backend().SetSpeedLimit({ enabled: true, kbps: 512 })
} catch (e) {
  toast('error', errorMessage(e))   // a Go error arrives as a plain string
}
```

The bindings are typed by hand in `src/wails.d.ts`, not imported from the generated `wailsjs/`
folder: one file to read, with the types from `types.ts`. Wails regenerates `wailsjs/` on every
build; it is committed, but nothing imports it.

**Adding a binding:**

1. Add the exported method to `App` in Go (`*_app.go` at the repository root).
2. Add its signature to `AppBindings` in `src/wails.d.ts`, and its data types to `src/types.ts`,
   using the Go struct's JSON field names.
3. Add a stand-in to `src/dev/mockBackend.ts` (in `extras`), or `npx tsc -b` fails.

**Empty lists can arrive as `null`.** Go sends a nil slice as `null`, not `[]`. Bindings that
return lists should return an empty slice, and the UI should still read them as `list ?? []`.

### Events

The backend pushes changes as events. `onEvent(name, callback)` returns the function that stops
listening, which fits `useEffect`'s cleanup:

```ts
useEffect(() => onEvent<ExtractResult>('extract:done', (r) => { /* … */ }), [])
```

| Event | Carries |
|---|---|
| `downloads:updated` | a `Download` that changed (status, name, size) |
| `downloads:progress` | `Progress` for running downloads, at most every 250 ms |
| `app:notice` | a message to show as a toast |
| `app:add-url` | a link from a second launch or the browser: open Add URL with it |
| `media:progress`, `media:changed` | video and gallery downloads (they run outside the list) |
| `extract:done` | an archive's extraction result, or that it needs a password or 7-Zip |
| `torrents:progress` | torrents' rows; the status bar sums their upload speed |
| `helpers:progress` | yt-dlp, ffmpeg or gallery-dl being installed |

Other events (`queues:done`, `datacap:changed`, `power:countdown`, `remote:changed`,
`torrents:changed`, `debrid:*`) are emitted for screens that don't exist yet.

## Conventions

- **Dialogs.** `App.tsx` keeps one `dialog` state, a union of `{ kind: 'settings' }`,
  `{ kind: 'checksum'; d }` and so on, and renders the matching component. A new dialog adds a
  kind there and uses `Modal` for its frame.
- **Toasts.** Results and errors are reported with `toast('ok' | 'error' | 'info', text)`.
  `call(fn, failure)` in `App.tsx` runs a backend call and toasts its error after the `failure`
  text.
- **Styling.** `style.css` holds the whole look, with named classes (`btn`, `field`, `modal`…)
  and colour tokens on `:root`. Tailwind supplies only its base reset; the components don't use
  utility classes.
- **Icons** come from `lucide-react`.
